## 0-1. 연결 서비스로 넓힌 뒤 다시 보는 전제 (2026-09-11, 논의 중)

사용자가 '저자 혼자 쓰는 도구'가 아니라 **출판사·편집자·독자와 연결되는 서비스까지**를 원한다고 정했다.
원고를 남에게 보여 주는 순간 서버·계정·공유가 생기므로, 앞서 정한 전제 일부를 다시 본다. 아래 '권하는 방향'은 아직 확정이 아니다.

| 앞서 정한 것 | 연결 서비스에서 생기는 일 | 권하는 방향 |
|---|---|---|
| Windows 데스크톱 · 원고는 저자 PC | 보여 주려면 서버가 필요하다 | **저자는 데스크톱 집필실, 상대(편집자·출판사·독자)는 설치 없이 웹.** 원고 전체는 저자 PC 에 두고, 저자가 고른 범위만 서버에 올린다 |
| 원고는 서버에 가지 않는다 | 공유분은 서버에 간다 | **공유는 저자가 고른 범위·상대·기간만**, 언제든 회수, 누가 언제 열람했는지 기록 |
| 한 번에 한 기기 · 저자 클라우드 폴더로 넘기기 | 어차피 서버가 생긴다 | 넘기기 통로를 **우리 서버의 종단 간 암호화 보관**으로 바꾸는 것을 검토(서버는 내용을 못 읽고, 클라우드 폴더 설정이 필요 없어진다) |
| 저자가 자기 키 | 출판사·편집자 쪽 AI 기능은 누구 키인가 | 저자 기능은 저자 키 유지. 상대 쪽 AI 기능은 플랫폼이 부담하고 그쪽 요금에 반영 |
| 저자 구독 | 돈을 낼 수 있는 편이 여럿이 된다 | 저자는 도구 구독. **출간 보장·유료 노출은 팔지 않는다**(돈 내고 보여지는 구조는 신뢰를 잃는다) |
| DB 로 관리 | 공유본·의견·투고 이력·계정이 생긴다 | 저자 원고 DB(저자 PC) + 서비스 DB(서버) 둘 |

### 연결마다 성격이 다르다

| 연결 | 저자가 얻는 것 | 어려운 점 | 권하는 순서 |
|---|---|---|---|
| 편집자·베타리더 | 원고 의견 | 적다 — 저자가 아는 사람을 초대하면 된다 | **먼저** |
| 출판사 | 투고·계약 | 출판사가 들어와야 한다(닭과 달걀) | 둘째 — 혼자 쓰는 '투고 관리'로 시작해 출판사 투고함으로 |
| 독자 | 연재·반응·팬 | 독자를 모아야 하고, 기존 연재 서비스와 경쟁하며, 신고·관리 운영이 무겁다 | 마지막, 검토 후 |

### 연결 서비스의 원칙 (추가)
- **상대도 의견만 낸다.** 편집자·베타리더는 원고를 직접 고치지 않고 의견·수정 제안을 남기며, 반영은 저자가 한다 — AI 검토자와 같은 자리(원칙 1).
- **공유는 좁게, 기록은 남게.** 범위·상대·기간을 저자가 정하고, 열람 기록을 남긴다(기획 도용 걱정에서 저자를 보호).
- **출판사에 가는 것은 표준 기획서 + 저자가 동의한 신뢰 정보**(출처 확인 상태, AI 기여 보고서). 다만 기여 기록은 저자 PC 에서
  만든 것이라 **위·변조를 완전히 막을 수 없다** — '인증'이 아니라 '자기 기록'이라고 정직하게 표시한다.
- **상대는 설치하지 않는다.** 웹 링크로 연다.

### 다시 짠 출시 단계 (안)
1. **혼자 쓰는 도구 + 투고 준비** — 8절의 1단계 + **투고 관리**(보낸 곳·날짜·회신 기록).
2. **내 사람들과 연결** — 편집자·베타리더 초대(웹에서 읽고 의견), 의견 반영 흐름, 열람 기록 · 탈고 도구.
3. **출판사와 연결** — 출판사 계정·투고함, 표준 기획서 수신·회신 · 전자책.
4. **독자와 연결** — 연재·반응(검토 후).

출시 전 확인 필요: 개인정보·계정, 공유 원고 유출 시 책임, 약관·신고 처리, 결제, 저작권 분쟁 대응.

### 정한 것 (0-1, 2026-09-11)
- 첫 연결 **편집자·베타리더** · 원고 보관 **저자 PC(공유분만 서버)** · 수익 **편집 서비스 수수료** · 편집자 연결의 폭 **나중에**.

### 풀어야 할 어긋남 — 수수료와 장터
- **수수료는 돈이 오가는 편집 거래가 플랫폼 안에서 일어나야 생긴다.** 그런데 첫 연결은 '저자가 아는 편집자·베타리더 초대'이고,
  플랫폼에서 편집자를 찾는 장터는 나중으로 정했다. 이대로면 **장터가 열리기 전까지 수익이 없다.**
- 아는 사이의 거래에 수수료를 붙이면 플랫폼 밖 직거래로 새기 쉽다(장터형 서비스의 흔한 문제).
- **권하는 안**: 장터가 열리기 전까지는 **저자 도구 구독을 유지**하고, 장터가 열리면 **편집 거래 수수료를 더한다.** 베타리더 초대는 무료.
- 확인할 것: 앞서 정한 구독을 유지하고 수수료를 더하는가, 구독 없이 수수료만으로 가는가(그렇다면 장터를 앞당겨야 한다).

## 1. 워크벤치에서 가져오는 것, 전제가 바뀌는 것

### 가져오는 개념

| 워크벤치 | 책 |
|---|---|
| 목차(`uid` 로 묶인 트리) | 부·장·절. 재배치가 잦아 `uid` 보존이 더 값지다 |
| 집필카드 | 장 설계서(이 장이 독자에게 주는 것 · 핵심 논점 · 분량) |
| 근거표 + 확정/진술 구분 | 출처함 + 주장-출처 연결 (5절) |
| `source_changed` | 출처를 고치면 그 출처를 쓴 장·문단에 신호 |
| 초고 제안 → 사람 채택 | 같다. 다만 채택한 뒤에도 AI 출처 표시가 남는다 (4절) |
| 검토자는 의견만 | 편집자·교정자 역할과 같다 |
| 엄격 모드 `[확인 필요]` | AI 문장의 사실 주장은 출처에 묶이거나 `[확인 필요]` 로 남는다 |
| AI 등급(빠름·기본·정밀, v0.26) | 그대로 |
| 스냅샷·자동 백업 | 몇 달짜리 작업이라 더 중요하다 |

### 전제가 바뀌는 것

- **'서버를 두지 않는다'의 이유가 바뀐다.** 워크벤치는 행정망 제약 때문이었고, 책은 **원고가 저자의 가장
  민감한 자산**이기 때문이다(유출·학습 걱정 없음). 결론(로컬 우선)은 같아도 이유가 다르므로,
  동기화 같은 편의 기능은 이 이유를 해치지 않는 방식으로만 붙인다.
- **설치 최소 → 일반 앱 수준의 설치.** `.bat`·파이썬 창은 일반 저자에게 쓸 수 없다. 설치 파일 하나와 자동 업데이트가 필요하다.
- **키 저장.** 워크벤치는 DB 에 평문으로 두었다(행정망에서 추가 설치가 곤란해서). 일반 앱은 **운영체제 자격 증명 저장소**
  (Windows 자격 증명 관리자 · macOS 키체인)에 둔다.

### 코드 관계 — 권하는 설계
**저장소는 따로, 모듈은 골라서 옮긴다.** 배포(데스크톱)·저장(블록 단위)·화면이 모두 달라, 엔진을 한 코드로 공유하면
양쪽이 서로의 제약에 묶인다. 옮겨 쓸 후보: 문서 읽기(`doc_read`), AI 어댑터·등급 설정, 근거 번호·표시 규칙, .docx 조립.

## 2. 설계 원칙 (워크벤치 원칙을 책에 맞게 다시 씀)

1. **AI 는 제안하고 저자가 확정한다. AI 가 쓴 문장은 채택해도 표시가 끝까지 따라간다.**
2. **책의 사실은 한곳에서 관리한다.** 출처·경험·설정이 바뀌면 그것을 쓴 곳에 신호가 간다. 확정 전엔 근거가 아니다.
3. **원고는 저자의 것이다.** 저자 PC 에 두고, 저자가 고른 AI 회사와 저자가 고른 사람에게만 보내며, 언제든 전체를 사람이 읽을 수 있는 형태로 꺼낼 수 있다.
4. **나중에 붙일 수 없는 것은 처음부터 한다.** AI 기여 추적·블록 이력은 소급할 수 없다.
5. **출판 실무의 언어를 쓴다.** 원고 · 꼭지 · 퇴고 · 교정 · 탈고 · 투고 · 원고지 매수 · 판권면.

## 3. 책의 사실 — 세 종류 (장르 공통 구조)

워크벤치의 **확정 근거 / 담당자 진술** 에 **설정** 하나를 더하면 세 장르가 한 구조에 들어간다.

| | 논픽션 | 에세이 | 소설 |
|---|---|---|---|
| 구조 단위 | 부·장·절 | 부·꼭지 | 장·장면 |
| 책의 사실 | **출처**(인용·통계·사례) | **저자의 경험**(= 진술) | **설정**(인물·연표·세계관) |
| 핵심 검토 | 사실확인·논리·중복 | 목소리 일관성·반복·감정 과잉 | 설정 일관성·시점·속도감·인물 말투 |
| AI 가 잘하는 일 | 구조 설계, 설명 다듬기, 예시 제안 | 문장 다듬기, 꼭지 배열 | 장면 초안, 대사, 묘사 변주 |
| **AI 가 위험한 일** | 가짜 인용·출처 없는 수치 | 없는 경험을 지어냄 | 설정 위반, 문체 평준화 |

논픽션 안에서도 **저자의 경험·인터뷰**가 섞인다(실용서·경험서). 그 부분은 진술 표시를 쓴다.

## 4. AI 설계

### 개입 수준 — 장마다 고른다
1. **편집자**: 의견만 낸다.
2. **제안**: 초안·다시 쓴 문장을 내고 저자가 채택한다.
3. **공동 집필**: 이어쓰기, 확장, 문체 맞춰 다시 쓰기.

### 저자의 목소리
- 저자가 직접 쓴 문단에서 **문체 견본**을 뽑아 AI 에 넘긴다.
- 퇴고 검토에서 AI 문단의 문체가 저자 문단과 어긋나는지 짚는다(AI 문장이 쌓이면 평균적인 문체로 흐른다).

### AI 기여 추적 — 원칙 4 (처음부터)
- 원고를 **문단 블록** 단위로 저장하고, 블록마다 출처를 기록한다: **사람 / AI / AI 후 사람이 고침**(+ AI 원문 보관 → 고친 정도 계산).
  연결 서비스에서는 **편집자 제안 채택**이 더해진다(6-1절).
- 문장 단위가 아니라 문단 단위인 이유: 한국어 문장 분리는 편집 중에 자주 흔들리고, 고지·판단에는 문단 단위와 글자 수 비율이면 충분하다.
- 내보낼 때 **장별 AI 기여 보고서**를 만들 수 있다.
- 배경(출시 전 확인 필요): 한국은 문화체육관광부 안내서(2023)에서 AI 산출물 자체를 저작물로 보지 않는다는 입장이고,
  출판 계약·공모전에서 AI 사용 고지를 요구하는 곳이 늘고 있다. 저자가 "이 원고의 AI 비중"에 답할 수 있어야 한다.

### 긴 원고 — 요약 계층
- 원고가 20만~40만 자라 통째로 AI 에 넣지 않는다. (첫 책인 자기계발서 약 200쪽은 12만~14만 자 안팎이라
  긴 문맥 모델에는 전체가 들어간다 — 그 경우 전체 검토는 원문으로 하고 요약은 구조 보기·비용 절감에 쓴다. 5-1절)
- 장마다 **저자가 확정한 요약**을 두고, AI 는 책 전체 흐름을 요약으로 보고 세부는 해당 장만 본다.
- 요약에도 '확정 전엔 근거가 아니다'를 적용한다(AI 가 만든 요약을 저자가 확정해야 전체 검토의 재료가 된다).

## 5. 논픽션 설계 (첫 장르)

### 출처함
- 출처 종류: 책 · 논문 · 기사 · 통계 · 웹 문서 · 인터뷰(→ 진술) · 저자 메모.
- 서지 정보: 저자, 제목, 출판사·매체, 연도, 쪽, URL, 접근일. 원본 파일(PDF 등)은 보관한다.
- **주장 ↔ 출처** 연결에 **인용 유형**을 둔다: 직접 인용 / 요약·재진술 / 수치 / 사례.
- 출처를 고치거나 원본을 바꾸면 그 출처를 쓴 문단에 신호.

### AI 가 문장을 쓸 때의 사실 규칙 (차별점)
- **AI 가 쓴 문장이라도 사실 주장은 출처에 묶이거나 `[확인 필요]` 로 남는다.** 워크벤치 엄격 모드와 같다.
- AI 는 출처를 지어내지 않는다. 출처함에 없는 책·논문·수치를 본문에 넣으면 사실확인 검토가 짚는다.
- (나중) 웹 검색을 붙이더라도 결과는 출처함에 **'미확인'** 으로 들어오고, 저자가 원문을 본 뒤에만 근거가 된다.

### 인용·저작권 관리 (출시 전 확인 필요)
- 직접 인용이 길면 표시한다(저작권법의 '정당한 범위' 판단은 저자·출판사 몫이므로 막지 않고 알린다).
- 출처 없는 직접 인용, 사용 허락이 필요한 그림·표에 **허락 상태**(받음 / 필요 / 해당 없음)를 둔다.

### 검토자 구성

| 검토자 | 보는 것 |
|---|---|
| 사실확인 | 주장 ↔ 출처 일치, 수치·날짜가 출처 값과 같은지, 출처 없는 주장 |
| 논리·구조 | 장 사이의 흐름, 중복, 빠진 연결, 주장-근거-결론 |
| 독자 | 대상 독자(입문자)가 막히는 곳, 용어 설명 누락 |
| 전문가 | 분야 관점의 정확성·반론 |
| 출판 편집자 | 시장성, 제목·장 제목, 기획 의도와 원고의 일치 |
| **규칙 검사(AI 없음)** | 용어 표기 흔들림(용어집 기준), 숫자·단위 표기, 반복 표현, 인용 부호 짝, 장별 분량 불균형 |

### 이미 쓴 원고 가져오기 (원고가 있는 저자용 → 2단계. 첫 책은 기획 단계라 기획 문서 가져오기가 먼저다 — 5-1절)
- .hwp / .hwpx / .docx / .txt 를 읽어 **부·장·절과 문단 블록**으로 나눈다. 장 제목 인식은 제안이고, 나누는 선은 저자가 확정한다
  (워크벤치 가이드라인의 '읽을 범위는 사람이 고른다'와 같은 이유 — 조용히 틀린 구조가 가장 위험하다).
- 가져온 블록의 출처 표시는 **'가져옴 — 작성 경위 모름'** 이다. '사람이 씀'으로 적지 않는다.
  앱 밖에서 어떻게 쓰였는지 우리는 모르기 때문이다(기여 보고서가 거짓말이 되면 안 된다). 저자가 원하면 '내가 씀'으로 확인할 수 있다.
- 원고 속 인용·수치는 출처가 비어 있는 주장으로 모아 보여 준다 → 출처함 채우기의 첫 할 일 목록이 된다.

### 책의 구성 요소
머리말 · 부/장/절 · 맺음말 · 각주 또는 미주 · 참고문헌 · 용어집 · (나중) 찾아보기.

### 투고는 기획서가 먼저다
- 논픽션은 **원고를 다 쓰기 전에 출간기획서와 샘플 원고로 계약하는 경우가 흔하다.**
  그래서 첫 결과물은 전체 원고가 아니라 **투고 패키지**다.
- 출간기획서 항목: 가제 · 기획 의도 · 핵심 메시지 · 대상 독자 · 비교 도서와 차별점 · 저자 소개(강연·연재·SNS 등) ·
  목차 · 샘플 원고(2~3장) · 예상 분량(원고지 매수) · 집필 일정.
- **비교 도서는 AI 가 지어내지 않는다.** 저자가 실제 책을 넣고, AI 는 차별점 문장만 다듬는다.

## 5-1. 첫 책 — 자기계발서 (기획 단계)

> 2026-09-11 사용자 답: 자기계발 · 약 200쪽 · 기획만 있음 · 한글 파일 · 인용·통계 수집 중.
> 1단계는 이 책 한 권을 기준으로 설계한다.

### 이 책이 바꾸는 우선순위
- **가져올 원고가 아직 없다.** 1단계 첫 입구는 '원고 가져오기'가 아니라 **기획 문서 가져오기**(한글)와 **자료 수집**이다.
  원고 가져오기는 2단계로 내린다(이미 쓴 원고가 있는 다른 저자에게는 여전히 필요하다).
- **지금 하고 있는 일이 수집이다.** 출처함은 '집필 뒤에 채우는 곳'이 아니라 **지금 매일 쓰는 곳**이어야 한다.
- **200쪽은 원고지 600~700매, 12만~14만 자 안팎**(판형·조판에 따라 다른 어림). 긴 문맥 모델에는 원고 전체가 들어가는
  크기라 전체 일관성 검토를 원문으로 할 수 있다. 그만큼 한 번에 드는 토큰이 많아 **예상 비용 표시가 더 중요해진다.**

### 기획에서 목차로
- 한글 기획 문서를 읽어 **기획서 항목(가제·기획 의도·대상 독자·핵심 메시지·목차 초안)에 나눠 담기를 제안**하고, 저자가 확정한다.
  워크벤치의 '가이드라인을 읽어 목차·카드를 제안하고 사람이 고른다'와 같은 흐름이다.
- 자기계발서는 제목·부제의 비중이 크다. AI 가 **제목안 여러 개**를 내되 제안으로만 둔다.

### 자기계발 장 틀 (집필카드 기본값)
틀은 기본값일 뿐이고 장마다 저자가 고친다.

| 칸 | 적는 것 |
|---|---|
| 독자의 고민 | 이 장이 푸는 문제를 독자의 말로 |
| 핵심 메시지 | 한 문장 |
| 여는 이야기 | 사례·일화 — 종류를 고른다(아래) |
| 근거 | 연구·통계·인용 — 출처함에서 연결 |
| 방법 | 단계 또는 원칙 |
| 실천 과제 | 독자가 오늘 해 볼 것 |
| 분량 | 쪽 또는 원고지 매수 |

### 사실확인이 먼저 볼 곳 (자기계발서에서 흔한 오류)
- **출처가 틀린 명언.** 유명인 이름이 붙어 떠도는 인용문은 원출처가 없는 경우가 많다.
  원출처(책·연설·쪽)가 없으면 기본이 '출처 확인 필요'다.
- **연구 결과 부풀리기.** "○○대 연구에 따르면 누구나 …" — 연구가 말한 범위(대상·조건·효과 크기)보다 본문이 크게 말하는지 본다.
  워크벤치 사실확인의 '근거가 문장이 말하는 범위까지 뒷받침하는가'와 같은 규칙이다.
- **출처 없는 통계.** 수치에는 출처와 기준 연도가 붙어야 한다.

### 사례의 종류 — 지어낸 사례가 실제처럼 보이지 않게

| 종류 | 표시 | 함께 기록 |
|---|---|---|
| 저자 경험 | 진술 | — |
| 지인·인터뷰 사례 | 진술 | 동의 여부 · 익명화 여부 (알아볼 수 있는 사람의 이야기 — 출시 전 확인 필요) |
| 기사·책의 사례 | 출처 | 서지 정보 · 쪽 |
| 가상 예시 | 가상 예시 | 본문에서도 가상임이 드러나야 한다 |

- **AI 가 만든 사례는 기본이 '가상 예시'다.** "김 과장은 석 달 만에 …"처럼 이름·직함·수치를 붙여 실제 사례처럼 쓰면
  사실확인이 짚는다. 원칙 2 의 금지선(지어낸 것이 근거 있는 것처럼 보이는 것)이 자기계발서에서는 바로 이 자리에 있다.

### 수집 중인 자료를 받는 입구
- 책 구절 붙여넣기 + 쪽, 웹 기사(주소 + 본문 붙여넣기), 파일(한글·PDF·엑셀 통계표 — 워크벤치 `doc_read` 를 옮겨 쓴다).
- 들어올 때는 **'어느 장에 쓸지 모름'** 이 기본이다. AI 가 쓰일 장을 제안하고 저자가 배정한다(워크벤치 자료 분석의 `usable_for` 자리).
- 책 구절에 쪽 번호가 없으면 '쪽 확인 필요'로 둔다. 나중에 쪽 번호를 다시 찾는 일은 품이 많이 든다.

### 상투구 짚기
AI 문장은 자기계발서의 상투구("작은 습관이 큰 변화를 만든다")로 흐르기 쉽다. 흔한 표현은 규칙으로, 문맥상 뻔한 문단은 AI 의견으로 짚는다.

## 6. 데스크톱 · 동기화 · 키 · DB

### 로컬 우선
- 원고·출처·설정은 저자 PC 의 DB 에 둔다. AI 호출만 인터넷이 필요하고 나머지는 오프라인으로 된다.
- 원고는 **저자가 고른 AI 회사에만** 보낸다. 화면에 그 사실을 적는다(각 회사 API 의 데이터 정책은 약관 확인 필요).

### 동기화 — 권하는 설계
- **DB 파일을 클라우드 폴더(OneDrive·Google Drive·Dropbox)에 그대로 두지 않는다.** 두 기기가 같은 SQLite 파일을
  동기화하면 충돌 사본이 생기거나 파일이 깨질 수 있다.
- **1단계 — 기기 넘기기**: 한 번에 한 기기만 쓴다. '다른 기기에서 이어 쓰기'를 누르면 원고 꾸러미를
  **저자 암호로 암호화**해 저자의 클라우드 폴더에 올리고, 작업 기기 표시를 남긴다. 다른 기기가 받아서 이어 쓴다.
  클라우드 회사는 내용을 읽을 수 없다. 워크벤치의 '파일을 통로로 쓴다'와 같은 발상이다.
- **2단계(동시 편집)는 하지 않는다** — '한 번에 한 기기'로 충분하다고 정했다(2026-09-11).
  작업 기기 표시가 있는데 다른 기기에서 열면, 덮어쓰지 않고 **"다른 기기에서 작업 중입니다 — 넘겨받을까요?"** 를 묻는다.
  넘겨받기 전 상태는 백업으로 남긴다(되돌리기가 새 사고가 되면 안 된다 — 워크벤치 교훈).

### 저자 키
- **가입 문턱이 가장 높은 자리다.** 첫 실행 안내에 회사별 키 발급 순서를 단계별로 보여 주고, 연결 시험을 함께 둔다.
- 키는 운영체제 자격 증명 저장소에 둔다.
- **비용이 저자 지갑에서 나가므로 보이게 한다.**
  - 큰 작업(전체 원고 검토 등) 전에 **예상 토큰·예상 비용**을 보여 준다(가격표는 앱이 갱신할 수 있게 두고 '예상'이라고 적는다).
  - API 응답의 사용량으로 **책별·월별 사용 장부**를 남긴다.
  - **월 한도**를 정하면 넘기 전에 멈추고 묻는다.
- 비용 절감: 긴 원고에서 자주 바뀌지 않는 맥락(출처 요약·장 요약·문체 견본)을 앞에, 바뀌는 요청을 뒤에 두어
  각 회사의 프롬프트 캐싱을 활용한다.
- 등급별 모델(빠름·기본·정밀)은 워크벤치 v0.26 설계를 그대로 쓴다.

### DB 로 관리할 때 지킬 것
- **블록 단위 저장**(4절 기여 추적) + **블록 이력**(어제 판으로 되돌리기).
- 자동 백업(워크벤치의 하루 한 번 백업과 같은 발상).
- **언제든 전체 내보내기**를 약속한다: 사람이 읽을 수 있는 원고(장별 텍스트) + 출처 목록 + .docx.
  DB 에 원고가 갇힌다는 불안이 일반 저자에게는 선택을 가르는 이유가 된다.

### 구독 — 권하는 설계
- **키는 저자가 넣으므로, 구독료가 사는 것은 AI 사용량이 아니라 '계속 쓸 수 있는 도구'다.**
  모델 이름·AI 회사 API 변경 대응, 검토자·규칙 개선, 투고 서식·전자책 요구사항 갱신, 동기화(기기 넘기기).
  구독의 값이 화면에서 보이지 않으면 '키도 내가 넣는데 왜 돈을 내나'가 된다.
- **서버는 라이선스 확인과 공유(6-1절)에만 쓴다. 원고 전체는 서버에 가지 않는다**(원칙 3).
- **오프라인 유예**: 확인을 못 해도 일정 기간은 그대로 쓴다(인터넷이 끊겼다고 글쓰기가 막히면 안 된다).
- **구독이 끝나도 원고는 열리고 꺼낼 수 있다.** 새 AI 기능·동기화만 멈추고, 읽기·전체 내보내기(원고·출처·.docx)는
  계속된다. 원고를 볼모로 잡는 순간 '원고는 저자의 것'이 무너진다.

### Windows 만
- 포장은 Windows 설치 파일 하나 + 자동 업데이트. 키는 Windows 자격 증명 관리자.
- 한국 저자의 기획 문서·수집 자료·원고는 **한글(.hwp/.hwpx)** 인 경우가 많다 → 한글에서 가져오는 입구가 첫 실행의 핵심이다(첫 책도 기획 문서가 한글).
  워크벤치의 `doc_read`(hwp/hwpx/docx 읽기)를 옮겨 쓸 수 있는 자리다.

## 6-1. 편집자·베타리더 연결 (첫 연결 · 2단계)

> 2026-09-11 첫 연결 상대로 정했다. 원고는 저자 PC 에 있고, 저자가 고른 공유본만 서버에 간다. 아래는 권하는 설계다.

### 두 역할

| | 편집자 | 베타리더 |
|---|---|---|
| 하는 일 | 전문 피드백 | 독자로서의 반응 |
| 남기는 것 | 수정 제안(원문 → 제안문) · 구조 의견 · 사실 질문 | 반응(좋음 · 지루함 · 이해 안 됨 · 더 알고 싶음) + 한마디 · 저자가 만든 질문에 답 |
| 원고를 고치나 | 아니다 — 제안만, 채택은 저자 | 아니다 |

### 공유하기
- 저자 PC 에서 **범위**(기획서 / 장 / 원고 전체), **상대**(이메일), **기간**을 정해 공유본을 만든다.
- 공유본은 그 순간의 **판**이다. 저자가 계속 고쳐도 상대는 받은 판을 보고, 새 판을 보내면 판 번호가 오른다.
- 상대는 **설치 없이 웹**에서 연다. 계정은 최소(이메일 인증). 저자는 혼자 쓸 때 계정이 필요 없고, 공유할 때만 만든다.
- 공유본은 **종단 간 암호화**를 권한다: 서버에는 암호문만 두고, 푸는 키는 초대 링크 중 서버로 보내지 않는 부분에 담는다.
  이메일 인증까지 해야 열리게 해, 링크만 새어서는 바로 열리지 않게 한다.
  - 대가: 서버가 내용을 볼 수 없으므로 신고·분쟁 때 내용을 확인하려면 저자나 상대의 제출이 필요하다(출시 전 확인 필요).
- 열람 화면에 **열람자 이름 워터마크**, 복사·내려받기 제한. 다만 화면을 찍거나 옮겨 적는 것은 막을 수 없다 —
  **억제이지 차단이 아니라고** 저자에게 정직하게 알린다.
- **열람 기록**: 누가 언제 어느 장을 열었는지. 베타리더가 '어디까지 읽었나'는 **베타리더가 동의할 때만** 모은다.
- **공유 끝내기**: 서버의 공유본을 지워 더는 열리지 않게 한다. 이미 본 내용은 되돌릴 수 없다는 것도 알린다.

### 의견이 저자에게 돌아오는 길
1. 상대가 웹에서 **문단에 의견**을 단다. 의견은 문단 블록의 고유번호(+ 선택 구간)에 매달린다
   — 워크벤치에서 목차 고유번호에 카드·근거를 묶던 방식과 같다.
2. 저자 앱이 서버에서 의견을 받아 **저자 PC DB 에 저장**하고, AI 검토자 의견과 같은 목록에 쌓는다.
   상태: 미처리 · 반영 · 반영 안 함 · 보류.
3. 새 판을 보낸 뒤에도 의견은 문단을 따라간다. **가리키던 문단이 그 뒤 바뀌었으면 '원문이 바뀜'** 을 표시한다
   (워크벤치의 `source_changed` 와 같은 신호).
4. **수정 제안을 채택하면 기여 기록에 '편집자 제안 채택'** 이 남는다. 사람 편집자의 기여도 AI 기여처럼 기록된다
   — 감사의 말·계약 때 근거가 된다.
5. (선택) 반영했음을 상대에게 알린다.

### 베타리더 반응 모아 보기
- 장·문단별 반응 분포, 저자가 만든 질문에 대한 답 모음.
- 동의한 베타리더에 한해 **읽기를 멈춘 지점** — 자기계발서에서 '지루해서 덮게 되는 장'을 찾는 데 쓴다.

### 수익과의 관계
- 베타리더 초대는 무료.
- 편집 서비스 수수료는 **돈이 오가는 편집 거래**에서 생기므로, 장터(편집자 연결의 폭)를 정할 때 결제·정산·세금·분쟁 처리와
  함께 설계한다(0-1절의 '풀어야 할 어긋남'). 출시 전 확인 필요.

## 7. 결과물

### 투고 패키지 (.docx)
- 출간기획서 + 목차 + 샘플 원고, 투고용 원고 서식(글꼴·줄 간격·여백·쪽 번호), 원고지 매수 환산.

### 전자책 (EPUB3)
- 구성: 표지 · 목차 · 장별 본문 · 각주 · 메타데이터. 파일 구조 자체는 표준 라이브러리로 만들 수 있다.
- 서점 유통 전에 검증 도구(EPUBCheck)를 통과해야 하고, 서점·유통사마다 요구사항이 달라 확인이 필요하다.

### 각주·참고문헌 형식
- 각주 / 미주 / 참고문헌 목록 중 고르고, 서지 표기는 몇 가지 형식 중 고른다(출판사마다 다르다).

## 9. 하지 않기로 한 것 · 주의

- **DB 파일 자체를 클라우드 폴더로 동기화하기** — 파일이 깨질 수 있다.
- **AI 가 출처·비교 도서를 만들어 넣기** — 논픽션의 신뢰가 무너진다.
- **기여 추적을 나중에 붙이기** — 소급할 수 없다.
- **두 기기 동시 편집** — 한 번에 한 기기로 충분하다(2026-09-11 결정). 다른 기기의 작업을 덮어쓰지 않고 넘겨받기를 묻는다.
- **구독이 끝나면 원고를 못 열게 하기** — 읽기·전체 내보내기는 계속된다.
- **원고 전체를 서버에 올리기** — 원고는 저자 PC 에 두고, 서버에는 저자가 고른 공유본만 간다(2026-09-11 결정).
- **가져온 원고를 '사람이 씀'으로 적기** — 작성 경위를 모르므로 '가져옴'으로 적는다.
- (장르 확장 시) **에세이에서 저자 진술에 없는 경험을 AI 가 단정하기** — 짚어서 표시한다.

## 10. 열린 질문

> 운영체제(Windows)·동기화(한 기기)·가격(구독)·첫 책(자기계발서, 기획 단계)은 2026-09-11 정해졌다(0절·5-1절).
> 기획 문서의 내용·자료 수집 습관·장의 모양·저자 소개 칸은 사용자 답이 "특별한 요구 없음"(2026-09-11)이라
> 아래 기본값으로 간다. 실제로 써 보다가 막히는 자리에서 고친다.

### 기본값으로 정한 것
- **기획 문서 가져오기** — 형식을 가정하지 않는다. 자유 형식 한글 문서를 읽어 기획서 칸 배분을 제안하고 저자가 확정한다.
  칸에 맞지 않는 내용은 버리지 않고 '메모'로 남긴다.
- **수집 입구** — 붙여넣기(구절 + 쪽)와 파일(한글·PDF·엑셀)이 기본. 브라우저 확장·메모 앱 연동은 실제 습관이 확인되면 붙인다.
- **장 틀** — 5-1절의 자기계발 장 틀을 기본값으로 쓴다. 장마다 칸을 빼거나 더할 수 있다.
- **저자 소개 칸** — 일반 입력칸. AI 는 문장 다듬기만 하고 이력은 지어내지 않는다.

### 아직 남은 질문
1. **구독과 수수료의 관계** — 구독을 유지하고 장터가 열리면 수수료를 더할지(권함), 구독 없이 수수료만으로 갈지. 0-1절.
2. **편집자 연결의 폭** — 아는 사람 초대만 / 장터까지. 나중에 정하기로 했다(2026-09-11).
3. **제품 이름** — 화면·설치 파일·문서에 쓸 이름.
