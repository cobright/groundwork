# 주민 설문 — 계획서의 논리를 세우는 장치

> 2026-10-13 사용자와 논의해 정한 방향. **아직 만들지 않았다.** 챌린지 제출(11.11) 뒤에 시작한다.
> GIS(읍·면 단계구분도)는 이 문서의 끝 '확장 버전'에 따로 적었다.

## 1. 출발점 — 사용자가 말한 것

> 공모사업 계획서는 이 사업을 하는 **근거·이유·배경**을 명확히 해야 한다. 객관적인 **통계**로 뒷받침할 수 있는
> 경우가 있고, **설문**으로 뒷받침해야 하는 경우가 있다. 이 자료를 바탕으로 사업의 **내용을 구체화**해야 한다.
> 설문은 사업이 만들어 낼 것(결과·프로그램·건물)을 **직접 이용할 주민의 의견**이라 매우 중요하다.
> 그래서 설문은 계획서 **각 단계의 근거**로 쓸 수 있도록 체계적이고 꼼꼼하게 구성되어야 한다.
> 요즘은 **구글폼·네이버폼**이 대부분이고 오프라인은 예외적이다. 설문의 시작에서 분석까지가 계획서에 매우 중요하다.

예전 경험에서 힘들었던 것: 설문 구성 / 내보낸 엑셀 정리(시간이 가장 듦) / 분석 결과의 설득력(가장 어려움).

## 2. 핵심 생각 — "설계한 설문지가 곧 분석 틀이다"

설문을 다 받은 뒤에 "이걸로 뭘 말할 수 있나"를 찾으면 늦다. 그때는 이미 빠진 문항을 되살릴 수 없고,
결과를 주장에 끼워 맞추게 된다. 그래서 순서를 뒤집는다.

```
 계획서의 주장  ──→  무엇으로 증명하나(통계? 설문?)  ──→  설문 문항  ──→  분석 계획
      ↑                                                                        │
      └────────────── 결과가 주장을 받쳐 주는가 (받쳐 주지 않으면 그대로 보인다) ←─┘
```

- **문항은 주장에서 나온다.** 문항마다 "어느 목차 항목의, 어떤 주장을 받치는가"가 붙는다.
- **분석은 설문 전에 정한다.** 문항마다 "무엇과 무엇을 견줄지"(예: 이용 의향 × 연령대)를 미리 적어 둔다.
  그러면 결과가 들어오는 순간 집계가 저절로 되고, 결과를 본 뒤 유리한 것만 골라 쓰는 일도 막힌다.
- **결과가 주장을 받쳐 주지 않으면 그대로 보인다.** 그것이 설문의 진짜 쓸모다 —
  주민이 원하지 않는 것을 알게 되면 **사업 내용을 고친다.** 설문은 계획서를 꾸미는 것이 아니라 사업을 빚는 것이다.

## 3. 통계와 설문의 역할 나누기 — "근거 지도"

계획서의 단계마다 받쳐야 할 주장이 있고, 그 주장에 맞는 근거의 종류가 다르다.

| 계획서 단계 | 받쳐야 할 주장(예: 스마트 경로당) | 주로 무엇으로 |
|---|---|---|
| 배경·필요성 | 고령화가 심하다, 독거노인이 많다 | **통계**(주민등록·행정 자료) |
| 〃 | 지금 경로당에 불만이 있다, 무엇이 부족하다 | **설문**(실태) |
| 수요 | 주민이 이런 것을 원한다, 이것이 가장 시급하다 | **설문**(수요·우선순위) |
| 사업 내용 구체화 | 이 프로그램·시설·운영 방식(요일·시간·장소)으로 하겠다 | **설문**(선호) + 담당자 진술 |
| 기대 효과·목표 | 연 ○○명이 이용할 것이다 | **설문**(이용 의향·빈도) × **통계**(대상 인구) |
| 지속가능성 | 주민이 운영에 참여할 것이다 | **설문**(참여 의향) |

규칙:
- **통계로 증명할 수 있는 것은 설문으로 묻지 않는다.** 군의 연령 분포를 설문으로 재면 틀리고, 문항만 길어진다.
- **설문으로만 알 수 있는 것**(원함·불만·선호·의향)에 문항을 쓴다.
- 워크벤치는 목차의 각 항목에 대해 이 표를 **제안**하고(가이드라인 분석의 배점·작성 안내가 출발점), 사람이 정한다.
  통계로 받칠 칸은 **자료요청**으로, 설문으로 받칠 칸은 **설문 문항**으로 이어진다.
- '근거 지도'에서 아무것으로도 받쳐지지 않은 주장이 남으면 그대로 표시한다(배점 ↔ 목차 짝짓기에서 빠뜨린 항목을 보여 주는 것과 같은 원리).

## 4. 흐름 — 결재란처럼 단계가 보이게

```
 ① 근거 지도 → ② 문항 설계 → ③ 점검 → ④ 폼으로 옮기기 → ⑤ 수집 → ⑥ 정리 → ⑦ 분석 → ⑧ 확정(근거)
```

### ① 근거 지도
위 3장. 목차 항목별로 "이 항목의 주장 / 통계로? 설문으로?"를 정한다.

### ② 문항 설계
- 설문으로 받칠 주장마다 문항을 **제안**(LLM)하고 사람이 고르고 고친다. 사람이 처음부터 써도 된다.
- 문항 하나에 붙는 것: 문항 글 · 유형(단일·복수·척도·순위·숫자·주관식) · 보기 · **목차 항목(uid)** · **받치는 주장** · **분석 계획**.
- **인적 문항은 분석에서 거꾸로 정한다.** 분석 계획에 "× 연령대", "× 읍·면"이 있으면 그 문항이 반드시 있어야 하고,
  보기는 **주민등록 통계의 구분과 똑같이** 만든다(그래야 6장 '응답자 ↔ 인구' 비교가 된다). 끝난 뒤엔 고칠 수 없는 실수라 여기서 막는다.
- **흐름(분기)**: "경로당을 이용하지 않는다" → 이유 문항으로. 폼의 '섹션 이동'으로 옮길 수 있게 적어 둔다.
- **이름·연락처는 묻지 않는 것이 기본**이다. 꼭 필요하면(경품 등) 개인정보 수집·이용 동의 문항을 함께 넣고, 분석 파일과 분리한다.

### ③ 점검 (검토자처럼 의견만)
- 문항 품질: 이중 질문("시설과 프로그램에 만족하십니까"), 유도 질문, 겹치거나 빠진 보기, 척도 불균형, '기타' 누락.
- 구조: **받치는 주장이 없는 문항**(빼도 되는 문항), **문항이 없는 주장**(빠진 문항), 분석 계획에 필요한 인적 문항 누락.
- 분량: 문항 수·예상 응답 시간. 길면 응답률이 떨어진다는 것을 알려 준다.
- **목표 응답 수**: 대상 인구(확정 근거에서)와 원하는 오차범위로 계산해 보여 준다(예: 경로당 회원 6,100명, ±5%p → 약 360명).
- **대상과 방식이 맞는지**: 사업의 실제 이용자(예: 70대 이상 어르신)가 온라인 폼에 잘 응답하지 않을 집단이면 그렇다고 말한다.
  대안은 오프라인 종이 설문이 아니라 **현장에서 담당자·도우미가 태블릿으로 같은 폼에 대신 입력**하는 것 — 폼 하나로 모인다.

### ④ 폼으로 옮기기
- 구글폼·네이버폼에 **그대로 옮겨 적기 좋은 형태**로 내준다: 문항 번호·글·유형(폼의 이름으로: 객관식/체크박스/드롭다운/선형 배율/
  객관식 그리드/단답/장문)·보기·필수 여부·'기타' 허용·섹션 이동.
- **폼 설정 점검표**를 함께 준다: 응답 1회로 제한할지, 필수 응답, 개인정보 동의, 응답 마감일, 응답 시트 연결.
- 폼을 API 로 직접 만들지 않는다 — 계정 인증이 필요하고 행정망에서 막힐 가능성이 크다(원칙 4).

### ⑤ 수집
워크벤치 밖(폼)에서 한다. 설문을 받는 서버를 두지 않는다(원칙 3·4). 중간에 내보내기 파일을 올리면 **응답 수와 응답자 구성**을
보여 줘서, 어느 집단이 모자라는지 수집 중에 알 수 있게 한다(그래야 현장 대리 입력으로 메울 수 있다).

### ⑥ 정리 (규칙)
내보내기 파일(구글: xlsx/csv, 네이버: xlsx)의 열을 **설계한 문항과 짝짓는다**. 문항을 워크벤치에서 설계했으므로 대부분
자동으로 맞는다 — 이것이 "설계한 설문지가 곧 분석 틀"의 실제 이득이다. 맞지 않는 열만 사람이 고른다.

정리 규칙(예전에 손으로 하던 것):
- 복수응답이 한 칸에 뭉친 것(`건강관리, 운동`) 나누기 — 보기 글에 쉼표가 들어 있을 수 있으므로 **설계한 보기 목록으로** 나눈다.
- `기타(직접 입력)` 응답을 보기와 떼어 주관식처럼 다루기.
- 척도 글 → 점수·순서.
- 표기 흔들림 모으기(`동산면`·`동산`·`동산 면`) — 모은 결과는 사람이 확인.
- 테스트 응답·중복 응답 후보 표시(지우는 것은 사람).
- 설계 없이 밖에서 만든 설문도 받는다(폴백): 이때는 열 머리글과 값으로 문항 유형을 **추정**하고 사람이 확인한다.

### ⑦ 분석 (숫자는 규칙, 해석만 LLM 제안)
- ② 에서 정한 분석 계획대로 빈도·비율·순위·교차표를 **규칙이 계산**한다.
- 주관식은 LLM 이 **분류와 대표 응답을 제안**하고 사람이 확정한다(개인정보를 가린 글만 보낸다).
- 결과마다 "이 결과가 어떤 주장을 받치는가 / 받치지 못하는가"를 나란히 보인다(2장).

### ⑧ 확정 → 근거
- 사람이 확정한 결과만 **`[설문]` 근거**가 되어 목차 항목(uid)에 묶인다. 초고·검토·최종본이 기존 근거처럼 쓴다.
- 근거의 성격이 새로 생기므로 `services/evidence.py` 의 `evidence_mark()`·`linked_evidence()` 와 함께 본다(6장 규칙).
- 응답 파일을 다시 올리면(추가 응답) 그 결과를 쓴 근거에 `source_changed` 신호가 뜬다 — 자료와 같은 규칙.

## 5. 설득력 — 숫자의 조건과 한계를 함께 보인다

심사위원이 설문 결과를 의심하는 이유는 대개 숫자가 아니라 **숫자의 조건이 안 보여서**다. 전부 규칙으로 계산한다.

1. **조사 개요가 숫자를 따라다닌다** — 대상·기간·방식(온라인 폼/현장 대리 입력 비율)·응답 수가 결과를 인용하는 모든 자리에 붙는다.
2. **오차범위** — 예: 응답 412명, 95% 신뢰수준 ±4.8%p.
3. **응답자 구성 ↔ 실제 인구** — 가장 강력한 장치. 확정 근거인 주민등록 인구와 나란히 놓아
   "응답자 중 70대 이상 18%, 실제 인구 31% — 고령층 의견이 적게 반영됨"을 **담당자가 먼저** 밝힌다. 필요하면 가중치를 준 결과를 함께 보인다.
4. **단정하지 않는다** — 교차표 칸의 표본이 작으면 "표본이 작아 차이를 단정하기 어렵다". 간단한 검정은 표준 라이브러리로.
5. **비교 기준이 없는 수치를 짚는다** — "만족도 62.4%"는 이전 조사·도 평균·전국 통계와 견줘야 뜻이 생긴다. 찾아 붙이는 것은 사람.
6. **주민 목소리 인용** — 사람이 고른 주관식 응답을 `[설문] 주관식 응답 중` 으로 인용.
7. **수요 → 목표의 계산 근거** — "이용 의향 64% × 대상 인구 6,100명 × 주 1.8회" 처럼 정량 목표를 **식으로** 보인다.
   목표 숫자가 어디서 나왔는지 보이는 계획서는 드물고, 그래서 강하다.

확정한 결과는 기존 검토자가 그대로 쓴다(예: 사실확인이 "412명 응답을 '군민 대다수'라 쓴 것은 과장"을 짚는다).

## 6. 반드시 지킬 것

- **숫자는 규칙이 센다.** LLM 은 문항 제안·주관식 분류·해석 제안만(원칙 2).
- **원자료는 밖으로 나가지 않는다.** 외부 AI 에는 집계 결과와 가린 주관식만 보내도록 **구조로** 막는다(호출부의 주의에 맡기지 않는다).
- **결과를 주장에 맞춰 고르지 않는다.** 분석 계획은 수집 전에 정하고, 받쳐 주지 않는 결과도 화면에 남긴다.
- 응답 원본 파일은 **딴 표**에 둔다(목록을 `SELECT *` 로 읽는 표에 BLOB 금지 — `resource_files` 와 같은 이유).
- 문항·근거 지도는 목차 **uid** 에 묶는다 → 새 테이블은 `put_outline` 의 정리 규칙과 `services/snapshot.py` 되돌리기에 반드시 넣는다(6장 규칙).
- AI 를 부르는 곳(문항 제안·점검·주관식 분류)은 `aiconfig.TASKS` 에 한 줄씩 더한다.
- 폼 연동(API)·설문 서버는 만들지 않는다.

## 7. 저장 모양(초안 — 만들 때 다시 본다)

```
surveys            id, project_id, title, target(대상), method, period_from/to, target_n, status(단계), created_at
survey_claims      id, survey_id, node_uid, claim(주장), basis('통계'|'설문'|'진술'), note          ← 근거 지도
survey_questions   id, survey_id, uid, sort, text, qtype, options(JSON), required, other_allowed,
                   claim_id, analysis(JSON: 견줄 문항 등), branch(JSON)
survey_files       id, survey_id, filename, data(BLOB), size, uploaded_at, column_map(JSON)        ← 딴 표
survey_results     id, survey_id, question_id, result(JSON), confirmed_at, evidence_id
```

화면은 헤더에 **'설문'** 탭 하나를 더하는 쪽(숨긴 메뉴로 접지 않는다 — 원칙 5). 탭 안에 ①~⑧ 단계 띠를 결재란처럼 보인다.

## 8. 만드는 순서(제출 뒤)

1. **근거 지도 + 문항 설계(사람이 쓰기) + 폼으로 옮기기 + 내보내기 짝짓기·정리 + 기본 집계** — 뼈대. AI 없이도 끝까지 돈다.
2. **설득력 장치**(5장) — 1 의 집계 위에 얹는다.
3. **AI 제안**: 근거 지도 제안, 문항 제안·점검, 주관식 분류.
4. (설계 없이 밖에서 만든 설문 받기 — 폴백 정리)

1 을 AI 없이 도는 뼈대로 두는 이유: 담당자 진술·가이드라인과 같다 — 폴백이 있어야 '빠른 길'이 막히지 않는다.

## 9. 시작 전에 필요한 것 — 실물

- **구글폼 내보내기 1개, 네이버폼 내보내기 1개**(응답자 정보를 지운 사본). 복수응답 구분자·척도 표기·기타 응답 위치·
  그리드 문항의 열 모양을 짐작으로 맞추면 실제 파일에서 반드시 깨진다.
- 가능하면 그 설문의 **문항지**와, 그 결과를 쓴 **계획서의 해당 부분**도 함께 — "문항 → 주장" 연결이 실제로 어떻게 쓰였는지 보기 위해서다.

## 확장 버전 — GIS

사용자가 가장 많이 쓰던 지도: **읍·면별 단계구분도**(예: 고령화율을 색으로) + **막대그래프**.

- 행정망 제약: geopandas·GDAL 같은 무거운 부품은 설치할 수 없고, 배경지도(타일)는 외부 서버가 필요하다.
- 그래서 범위를 좁힌다: **읍·면 경계(SHP)를 표준 라이브러리로 읽어 단계구분도 하나**부터. 경계 파일은 꾸러미에 미리 담는다
  (출처·이용 조건을 확인할 것). 설문·통계 결과를 읍·면별로 색칠하는 자리라 설문 기능과 이어진다
  (설문의 읍·면 문항 보기를 경계 파일의 읍·면 이름과 같게 만드는 이유가 하나 더 생긴다).
- **"지도도 근거다"** — 다른 곳에서 만든 지도 이미지를 출처·기준일·작성자와 함께 자료로 등록·확정하는 길을 먼저 연다.
- 배경지도 위의 위치도·정밀 공간분석은 워크벤치가 할 일이 아니다(군청 GIS 담당·기존 도구).
- 막대그래프는 엑셀 파일에 네이티브 차트로 담아 내주는 것이 행정망에서 가장 덜 낯설다(openpyxl 은 이미 꾸러미에 있다).
  그린 지도·그래프를 **최종본(docx/hwpx)에 그림으로 넣는 것**이 미리 확인할 어려운 지점이다.
